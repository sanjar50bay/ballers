BALLERS 0.2.12-alpha — единый экран игры и один ведущий

Состав релиза
- Подготовка игры: подтверждённые игроки, заполненные составы следующей пары,
  сохранённые капитаны, назначенный ведущий. Из списка можно перейти
  к исправлению; старт доступен после готовности всех пунктов.
- Готовый список сворачивается. Обычный игрок не видит настройки организатора.
- Капитаны и ответственные показываются выбранными только после сохранения;
  новые формы требуют явного выбора, ссылка из подготовки раскрывает форму.
- Пока есть LIVE/PAUSED матч, составы доступны для просмотра с пояснением.
- Известные ошибки подготовки показывают конкретное действие на RU/KK.
- При возвращении во вкладку данные запрашиваются сразу; устаревшие ответы
  обновления не перезаписывают уже полученные более свежие данные.
- Общая концепция: docs/PRODUCT_CONCEPT_RU.txt.
- Включает ещё не опубликованную навигацию PR #2.
- «Мои игры» — список ближайших игр и история. Карточка открывает единый экран.
- У игры вкладки «Обзор / Участники / Матчи», состояние вкладки хранится в URL.
- Формы команд, составов и приглашений переиспользуются; старые ссылки на участников
  перенаправляются в нужную вкладку. Ссылки на результаты и протокол сохранены.
- Организатор явно назначает одного ведущего. Все видят его имя.
- Текущие события, старт, пауза, продолжение и завершение — у назначенного ведущего.
  Менеджеры не получают неявного права управлять активным матчем после включения правил.
- Ведущий передаёт управление записанному игроку; организатор восстанавливает
  управление с причиной. Права меняются атомарно, история доступна читателям игры.
- После передачи старый ведущий теряет права; версия текущего матча повышается,
  поэтому записи со старого состояния второго устройства отклоняются.
- Исправления завершённых результатов остаются отдельным правом организатора
  с обязательной причиной, по существующим правилам строгого/доверенного режима.
- UUID операции старта сохраняется на устройстве до подтверждения. Повтор после
  обрыва связи возвращает прежний матч. Старый запрос с новой UUID и прежней
  последовательностью не запускает следующий матч после завершения предыдущего.
- Ведущий сохраняется между матчами игрового дня; скрытой смены на отдыхающую
  команду больше нет после включения новых правил.

Проверка
См. сохранённые логи сборки, lint, SQL и браузерных сценариев.
Новые проверки покрывают явное назначение, права, передачу, восстановление,
пять конкурирующих стартов, пять разных игроков, потерю ответа и повтор после
перезагрузки, устаревшие версии, запись гола и обновление статистики.
В браузере используются разные контексты пользователей и изолированный PGlite;
HTTP/OAuth имитируются. PGlite последовательно исполняет SQL транспорт:
это функциональные проверки конкурирующих запросов, не нагрузочный тест
многосоединительного рабочего PostgreSQL. Серверная сериализация обеспечена
блокировкой игрового дня и существующим уникальным индексом LIVE/PAUSED.
Исторические браузерные сценарии старого игрового центра требуют адаптации
к новым вкладкам/правам; актуальные сценарии нового центра — leader.browser.test.mjs.
В CI добавлен их запуск с настоящим браузером.

Порядок тестирования и публикации
1. Проверить, что в нужном Supabase-проекте применена миграция 008.
2. Применить 20261117_009_game_leader.sql ОДИН РАЗ.
   Установка не включает правила глобально. Старый клиент продолжает работать.
   Для уже активных матчей сохраняется текущий оператор; счета не переписываются.
   Затем применить 20261118_010_first_match_defaults.sql: первый запуск нового
   дня создаёт стандартные правила (7 минут / 2 гола), если правил ещё нет.
   Сохранённые организатором правила не перезаписываются. Это исправляет ошибку,
   найденную при проверке впервые созданного дня на рабочем Supabase.
3. Открыть Deploy Preview нового релиза. Создать отдельный тестовый игровой день.
   Явное назначение ведущего включает новые правила ТОЛЬКО для этого дня.
   После этого управлять тестовым днём следует из нового интерфейса.
4. Проверить организатора, ведущего и зрителя с разных устройств; передачу;
   обрыв связи и повтор запуска; гол, завершение, статистику и карточку.
5. Опубликовать согласованный клиент 0.2.12.
6. Применить activate_009_game_leader.sql: новые правила станут обязательными
   для всех дней. На днях без ведущего организатору нужно назначить человека.
7. Попросить игроков обновить старые вкладки приложения.

Возврат
rollback_009_activation.sql выключает глобальный режим и включение отдельных
дней, сохраняя матчи, операции и журнал. Затем вернуть предыдущий deploy.
Схему и историю не удалять; baseline и старые миграции повторно не запускать.

Ограничения
- Один ведущий — одна учётная запись человека, а не привязка к одному телефону.
  На двух его устройствах конфликты правок проверяются по версии состояния.
- Один активный матч на игровой день; арены с параллельными полями и турниры
  входят в отдельный запланированный этап.
- В этом релизе нет онлайн-оплаты, календаря арен и турнирной сетки.
- Рабочая база и основной сайт не обновляются автоматически созданием PR.

Упрощение команды и календарь (18.11.2026)
- По умолчанию открывается состав. Разделы «Состав / Игры / Управление»
  сохраняются в URL; управление доступно ответственному команды.
- Ближайшая игра видна рядом с составом. В календаре отдельные ближайшие
  и история (до 20 записей каждого вида), только явно связанные игры,
  к которым у текущего участника уже есть доступ.
- Ответственный назначает игру: сообщество, дата, время, место. Он должен
  также управлять выбранным сообществом. Если своего сообщества нет,
  создание возвращает в планирование этой же команды.
- Текущий подтверждённый состав получает приглашения внутри приложения;
  каждый подтверждает явку сам. Членство в сообществе не добавляется.
- UUID и параметры создания сохраняются до подтверждения ответа; повтор
  после обрыва связи/перезагрузки возвращает тот же день без новых приглашений.
- Это календарь команды, не бронь поля и не расписание повторяющихся игр.

Проверки команды
17 новых SQL сценариев (роли, приватность, актуальный состав, повтор, откат
транзакции). 15 браузерных сценариев сети/команд, включая потерянный ответ,
перезагрузку, личный ответ игрока и RU/KK 320px. Браузерный транспорт тестовый,
SQL реальный изолированный PGlite; это не нагрузочный тест рабочего PostgreSQL.
