# BALLERS 0.2.8 — надёжность и понятные роли

## Объём первого пакета
- Личные сообщества явно называются «Мои сообщества»; рядом отдельный переход в общий каталог. Общий каталог доступен авторизованным игрокам, а не только создателю. Поисковые подписи зависят от вкладки. Технический текст про TEST-профили убран из интерфейса; исключение синтетических профилей из каталога сохранено.
- На главной выбирается ближайший доступный через членство/участие день по дате и времени, текущий live — первым. Более дальняя запись «Иду» не скрывает более близкую игру сообщества. Заявка гостя теперь видна на главной ещё до принятия: ожидает решения / резерв / предложено место. Предложение места не означает автоматическое «Иду».
- Если подходящих игр нет: понятная подпись, один поиск игры и отдельное создание дня. При ошибке загрузки не утверждаем, что игр нет. Для выбранной игры поиск ниже называется «Найти ещё игру».
- В игровом центре явно показан контекст: игрок, оператор текущего матча или организатор этого дня. Обычному игроку — просмотр капитанов вместо выключенных форм назначения. Синтетических игроков может создавать только OWNER; кнопка скрыта от MANAGER. Проверка прав на сервере сохранена, роль привязана к конкретному сообществу. Это не введение новой глобальной роли.
- Открытые игры: понятное объяснение, отдельные состояния загрузки/ошибки/входа/пустого выбранного города. Авторизованному пользователю не предлагается войти заново только из-за пустого списка.
- Меню плюса объясняет игровой день, команду и сообщество; «Скоро» оформлено отдельным бейджем. Новые строки переведены RU/Қазақша.

## Что не утверждаем
В архиве 0.2.7 уже были серверные проверки прав и большая часть UI-условий. Сообщение «игрок видит всё» не доказывает возможность серверного обхода. На изолированном стенде проверяем чтение/изменение отдельно. Причину неполного общего каталога именно в действующем проекте без диагностики его данных не установили: SQL007 повторно задаёт известную глобальную функцию без фильтра по автору, не отключая RLS. Для диагностики есть отдельный read-only SQL.

Второй пакет не включён: LIVE-предварительная таблица и бомбардиры, крупная перестройка игрового центра, улучшения тактической доски/реального touch, новая приветственная страница с RU/KK-видео, показ Baller ID только при первом знакомстве и вручную. Текущая таблица всё ещё считает только подтверждённые результаты выбранного реального/тестового типа. Неоднозначные показатели «В заявках», числа мест/участников и подпись случайного распределения требуют отдельной сверки фактически считаемых данных.

## Шаг 1 — только база
До изменения сохраните резервную копию действующей базы и убедитесь, что знаете способ восстановления; сохраните копию рабочей папки. В Supabase выберите **BALLERS Test**, тот же проект, где уже применены 001–006 (ref `cupgzvetwptqavxzbccm`). Не используйте другой Astana Amateur Ballers.

В новом пустом запросе SQL Editor выполните целиком **`supabase/migrations/20261028_007_reliability.sql`** один раз, включая BEGIN/COMMIT. Отдельный SQL-файл идентичен файлу в ZIP. Он не удаляет аккаунты, профили, участие, составы или историю. Повторное применение блокируется. Не запускайте baseline и прежние миграции повторно. При ошибке остановитесь, не запускайте остаток запроса и не убирайте проверки истории.

После Success:
```sql
SELECT version FROM public.ballers_migration_history ORDER BY version;
```
Должна добавиться `20261028_007`. Миграция не публикует сайт.

## Затем — файлы, проверки и публикация
1. Распакуйте архив отдельно в `Музыка\ballers-alpha-0.2.8`. Это источник обновления, не новый Git-репозиторий.
2. Откройте PowerShell в **этой новой папке** и запустите:
```powershell
powershell -ExecutionPolicy Bypass -File .\UPDATE_EXISTING_PROJECT.ps1
```
Скрипт сохраняет `.git`, `.env*`, `.netlify` в прежней рабочей папке; не удаляет старые файлы и ничего не публикует.
3. Перейдите в **прежнюю рабочую Git-папку** и проверьте сборку:
```powershell
cd "$env:USERPROFILE\Music\ballers-alpha-0.2.2"
npm ci
npm run build
npm audit
```
При ошибке остановитесь. Не используйте `npm audit fix --force` автоматически.
4. Только после успешных проверок:
```powershell
git status --short
git check-ignore .env.local
git add .
git diff --cached --name-only -- ".env*" ".netlify"
```
`.env.local` должен быть игнорируемым, последний список — пустым. Никогда не публикуйте ключи. Просмотрите `git diff --cached --stat`, затем:
```powershell
git commit -m "Release 0.2.8: scoped roles, home requests and directory UX"
git push origin main
```
5. Дождитесь успешного Netlify deploy соответствующего commit. Затем проверяйте сайт. Локальный build не означает публикацию.

## После публикации — короткая проверка
- Игрок другого аккаунта видит команды/сообщества других авторов в «Найти», но не инструменты организатора в чужом игровом дне. Прямые серверные изменения тоже должны отклоняться.
- Участник сообщества видит ближайший ещё не начавшийся день; гость видит свою ожидающую заявку и резерв на главной.
- Организатор открывает последнее место → первый подаёт заявку, организатор принимает → второй подаёт, организатор принимает в резерв → первый отказывается → второй получает предложение и подтверждает сам. Проверить колокольчик, порядок, отсутствие переполнения.
- Для независимого прогона нужны организатор и два разных игрока (три аккаунта). Не удаляйте существующие аккаунты ради теста.
- Повторите RU/Қазақша на телефоне. Настоящие Google OAuth, Supabase Realtime/сеть, Safari и фоновые уведомления не эмулируются полностью локальным Chromium.
- Если каталога/ближайшего дня всё ещё нет — `docs/DIAGNOSTIC_0028.sql` только читает данные. Не исправляйте это выключением RLS.
