## Историческая инструкция для более ранних установок

Ниже — прежний порядок установки 001/002/003. После них всё равно нужна 004, как описано в новой инструкции.

## Если установлена только 001 (002 ещё нет)

1. Сохрани прежнюю папку и резервную копию тестовой БД. Распакуй архив в **новую** папку `ballers-alpha`.
2. В SQL Editor **BALLERS Test** выполни целиком файл:
   `supabase/migrations/20261012_002_integrated_alpha.sql`
   Затем выполни `supabase/migrations/20261013_003_navigation_community.sql`. Обе миграции выполняются транзакциями. **Не запускай baseline и 001 повторно.** При ошибке остановись и пришли текст ошибки, не продолжай запуск с неполной схемой.
3. Скопируй свой `.env.local` из прежней папки, если он настроен на BALLERS Test. Или создай его по `.env.example`. Нужны только URL и publishable key тестового проекта. Google Client Secret, service_role и секретные ключи в приложение не добавляй и в чат не отправляй.
4. Останови старый сервер Ctrl+C. Открой PowerShell **в новой папке**, затем:

```powershell
npm ci
npm run dev
```

5. Открой http://localhost:3000 и войди. Настроенный Google OAuth остаётся в Supabase; для нового localhost менять его обычно не требуется.
6. Открой свой Game Day → **«Игровой центр: матчи, правила и подтверждения»**. Старые приглашения и Team Builder доступны по ссылке обратно.

### Только для совершенно пустого тестового проекта

Порядок: `supabase/test_project_baseline.sql` → миграция 001 → миграция 002 → миграция 003. Baseline — реконструкция public-схемы, не backup Auth/Storage/Google OAuth. На существующую базу baseline не накатывать. К действующему проекту миграции этим архивом не применялись.

## Первый тест без 15 Google-аккаунтов

1. В игровом центре владелец нажимает **«Тестовые игроки +14»**. Это отдельные синтетические профили без авторизации. Ранее добавленные TEST-профили не дублируются.
2. Вернись в «Составы и приглашения» → Invite Members → **выбрать всех** → отправить приглашения. Участники получают INVITED, а не автоматическое Going.
3. Для теста вернись в игровой центр и нажми **«Все участники → Иду»**. В реальной игре игрок сам отвечает на уведомление; менеджер также может менять ответ, капитан — только для своих игроков при выданном разрешении.
4. В Team Builder: Build Teams → Randomize. Для 15 Going должны появиться 5 / 5 / 5. Fixed и Core + Fill также сохраняются.
5. В игровом центре назначь и сохрани капитана и ответственного каждой команды. Сохрани правила.
6. Выбери стартовую пару и команду, которая уступит при первой ничьей (обе вышли одновременно), сохрани стартовую пару.
7. Начни матч, добавь голы/ассист/сейв/автогол, проверь паузу и обновление страницы. При лимите голов матч заканчивается и очередь меняется. Следующий матч можно начать до подтверждения предыдущего.
8. Тестовые игроки не могут зайти в аккаунт и подтвердить матч. Для матча с тестовыми участниками менеджеру доступно **«Подтвердить тест с причиной»**. Такие результаты помечаются тестовыми и **не смешиваются с настоящей статистикой**.
9. Для настоящего сценария нужны минимум два аккаунта капитанов: каждый подтверждает результат своей команды. Спор решается менеджером с пояснением.

## Что связано в одном приложении

- Приглашение → личное уведомление внутри приложения → Иду / Возможно / Не иду.
- Going-пул, ручное управление ответами и массовые действия менеджера. Массовое изменение состоит из последовательных атомарных изменений игроков; при ошибке уже успешные ответы сохраняются.
- Полная игра → очередь ожидания; участники получают уведомление о наличии ожидающих. Освободившееся место предлагается первому ожидающему, **без автоматического Going**. Он принимает или отказывается; менеджер может убрать ожидающего.
- Постоянные базовые команды сообщества: сохранить текущие составы, загрузить в следующий Game Day только пришедших. Отсутствующие остаются в базе команды.
- Random / Fixed / Core + Fill; ручные перемещения и защищённое ядро; атомарный Team Builder.
- Настройки игроков на поле (1–11), мест, 2–8 команд; 30–7200 секунд, 1–99 голов, режим окончания. Снимок правил на матч.
- Победитель остаётся; ничья — более старая команда садится; FIFO отдыхающих. Лимит серии пустой по умолчанию. В этой alpha, если лимит выбран, правило явно указано: победитель отдыхает. Другие стратегии пока не реализованы.
- Оператор, сохранённый таймер, пауза, события с защитой от повторов, отмена, история составов.
- Подтверждения капитанов, спор, объяснённое решение менеджера, пересчёт verified-статистики без дублей.
- Минимальная выдача открытых игр по городу и вступление/резерв. Гость не становится автоматически членом сообщества.

## Границы alpha — важно

Это **локально проверенный прототип, не готовый публичный релиз**.

- Уведомления опрашиваются каждые 5 секунд, пока приложение открыто. Системного push и уведомлений на закрытом телефоне нет.
- Таймер восстанавливается из состояния БД. Завершение по времени инициирует открытый экран оператора/менеджера; фонового серверного планировщика нет. После истечения времени новый гол отклоняется сервером. Проверь этот сценарий на двух устройствах.
- Предложение места в резерве пока не истекает автоматически. Если человек молчит, менеджер вручную отклоняет его участие, чтобы предложить место следующему.
- Интерфейс пока RU + прежние EN-экраны, не полноценные EN/RU/KK. PWA, offline-ввод и нативные приложения не реализованы.
- Состав матча означает участие в заявке; фактические минуты/выходы/замены не отслеживаются. Сейвы ручные. Глобальная формула рейтинга не придумана.
- Лиги/турниры, бронирование арен, платежи, услуги тренеров/судей, социальная лента и AI-модули не входят в эту alpha.
- Исходные широкие authenticated SELECT-политики некоторых таблиц, права на поля профиля, Auth/Storage/grants требуют дальнейшего аудита. Новый закрытый snapshot не делает всю старую схему приватной.
- npm audit показывает 5 high в цепочке dev-инструментов. `npm audit fix --force` не запускать вслепую: он предлагает несовместимые изменения. Перед внешним выпуском нужны устранение рисков и повторная проверка.
- Миграция 002 протестирована на реконструированной схеме; реальные Supabase/PostgREST/OAuth и конкурентные запросы с разных устройств проверяются отдельно у тебя.

## Автоматические тесты

```powershell
npm run test
npm run lint
npm run build
```

108 SQL-проверок (45 + 51 + 12), структурный regression-тест связи таблиц. Браузерные результаты — в `docs/VALIDATION.md`. SQL работает в изолированном PGlite/PostgreSQL и не обращается к твоей БД. Подробнее — `docs/VALIDATION.md`.

Необязательный браузерный тест `tests/browser.test.mjs` требует отдельно установленного Playwright/Chromium. Он подменяет OAuth и HTTP-транспорт только фиктивного `example.supabase.co`, но исполняет реальные SQL/RLS внутри изолированной БД. Не запускай его против живой базы. Сначала build/start на 127.0.0.1:3012 с фиктивными env из `docs/VALIDATION.md`; затем `PLAYWRIGHT_MODULE` указывает на установленный Playwright. Это не зависимость рабочего приложения.
